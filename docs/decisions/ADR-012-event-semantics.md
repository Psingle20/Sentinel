# ADR-012: Event semantics and message envelope

- Status: Accepted; service names follow the ADR-020 rename (`Sentinel.Api` is `Sentinel.Gateway`)
- Date: 2026-10-28

## Context

Every step of the walking skeleton crosses a service boundary over Redis Streams ([ADR-008](ADR-008-event-transport.md)), with a transactional outbox and an inbox in each service's PostgreSQL database ([ADR-009](ADR-009-persistence-baseline.md)). Before the first message is sent, Sentinel needs one answer to: what crosses the boundary, how it is named and versioned, what metadata travels with it, and what delivery guarantees consumers may rely on. [ADR-003](ADR-003-dotnet-backend-platform.md) also left open whether contracts are schema-first.

## Constraints

- At-least-once delivery; consumers must be idempotent (Phase 02).
- Tenant, environment, service and incident identity travel with every message (implementation plan, universal definition of done).
- The building blocks contain no Sentinel concepts ([building-blocks evolution](../implementation/building-blocks-evolution.md)).
- Model output and telemetry are untrusted; message contents are validated at the receiving boundary.

## Decision

### What crosses a service boundary

| Kind | Example | Transport |
| --- | --- | --- |
| Integration event: something that happened, owned by its producer | `runtime.incident.opened` | Redis Stream for the producer's topic family; any service may subscribe |
| Integration command: a request for another service to act | `agentworker.investigate-incident` | Redis Stream owned by the target service; only that service consumes it |
| Bounded request/response | Executor's start confirmation (ADR-006), Ingestion's observation queries (ADR-007) | Synchronous HTTP, within a timeout |

In-process commands and queries, domain events, Runtime's event-sourced events and Temporal signals never cross a service boundary as messages.

### Names and streams

- Events are named `<producer>.<subject>.<past-tense-verb>`, for example `ingestion.observation.recorded`.
- Commands are named `<target>.<imperative-verb>-<object>`, for example `executor.execute-remediation`.
- Each message type maps to one stream. Event streams follow the topic families in architecture §56, for example `sentinel.observations` and `sentinel.incidents`. Command streams are `sentinel.<target>.commands`.
- Every service registers the message types it produces and consumes explicitly at startup, mapping each CLR type to its name, schema version and stream. Nothing is discovered by reflection.

### Envelope

Every message travels in the same envelope, implemented in `CleanArchitecture.BuildingBlocks.Infrastructure`:

| Field | Meaning |
| --- | --- |
| `MessageId` | Version-7 GUID, unique per message; the inbox deduplicates on it |
| `MessageType` | The stable name above |
| `SchemaVersion` | Integer version of the payload contract |
| `OccurredAt` | UTC time the producer created the message |
| `Producer` | Producing service, for example `sentinel-runtime` |
| `CorrelationId` | Ties every message in one flow together, for example one incident's investigation |
| `CausationId` | `MessageId` of the message that caused this one, when there is one |
| `Headers` | String key/value pairs: `traceparent` and `tracestate` for W3C trace context, plus consumer-defined identity |
| `Payload` | The contract serialized as UTF-8 JSON |

Sentinel defines its identity headers in `Sentinel.Contracts`: `sentinel-tenant-id`, `sentinel-environment-id`, `sentinel-service-id` and `sentinel-incident-id`. Every Sentinel message carries tenant and environment; the others are present when they apply. A consumer rejects a message whose headers do not match its payload's identity.

### Contracts and serialization

- Integration message contracts are C# records in `Sentinel.Contracts`. They are the source of truth: code-first, not schema-first. Messages are only exchanged between .NET services.
- Payloads use `System.Text.Json` with camelCase names and enums as strings. Strongly typed identifiers serialize as plain values (`Sentinel.Contracts.Primitives`).
- `Sentinel.Api` publishes its HTTP contract as an OpenAPI document generated by ASP.NET Core, and `Sentinel.Web` generates its TypeScript types from that document. The web app never sees integration messages.

### Versioning

- Within one `SchemaVersion`, changes are additive only: new optional fields. Fields are never renamed, removed or repurposed, and consumers ignore unknown fields.
- A breaking change publishes a new `SchemaVersion`. During the transition the consumer accepts both versions, and the producer moves to the new version only after every consumer supports it.
- A consumer that receives a version it does not support dead-letters the message with the reason, rather than guessing.

### Delivery guarantees

- Delivery is at least once. A message may arrive more than once, late, or out of order relative to messages on other streams.
- Consumers record `MessageId` in their inbox in the same database transaction as the effects of handling it. A duplicate is acknowledged without handling it again.
- Ordering holds only within one stream. Consumers that need ordering across sources use event time and, for incident state, the stream version (ADR-004).
- A message that fails repeatedly moves to `<stream>.dlq` with its failure reason after the configured maximum number of deliveries.

## Consequences

### Positive

- Every service uses one envelope, one naming scheme and one deduplication rule.
- Trace context and tenant identity follow a flow across every hop.
- Versioning rules allow services to be deployed independently.

### Negative

- Explicit registration adds a line per message type per service.
- Code-first contracts tie messages to .NET. A non-.NET consumer would first need schemas generated from the contracts.

## Follow-up work

- Implement the envelope, registry, outbox, inbox and Redis Streams adapter in the building blocks (Stage E).
- Add the identity header names and the first contracts to `Sentinel.Contracts` with the walking skeleton.
- Add the OpenAPI document to `Sentinel.Api` when its first endpoint is built.

## Revisit criteria

Revisit if a non-.NET service needs to consume messages, or if message volume makes JSON payloads a measured bottleneck.
