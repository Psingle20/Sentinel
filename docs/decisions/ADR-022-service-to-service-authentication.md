# ADR-022: Service-to-service authentication

- Status: Proposed
- Date: 2026-10-30

## Context

Sentinel's five services trust whoever can reach them. Internal HTTP routes, including Runtime's start confirmation, the control-plane routes the Gateway calls and the internal query and replay routes, accept any caller on the network, and Redis Streams carries observations, investigation reports, approvals and execution results without saying who wrote them ([threat model](../architecture/threat-model.md#open-risks), findings F-007 and F-013). The decisions that matter most are already protected another way: every approval and operator action is an ES256 attestation the receiver verifies ([ADR-006](ADR-006-remediation-control-path.md)). Everything else is not, so anything that reaches the internal network can read incidents, report findings, confirm an execution start or publish a fake observation.

Phase 09 cannot close without a decision, and the production deployment environment is not chosen yet. This proposal therefore separates what Sentinel's code must do, which can be decided now, from where identities come from, which depends on the environment.

The internal calls today:

| Caller | Receiver | Over | What for |
| --- | --- | --- | --- |
| Gateway | Runtime | HTTP | Incident queries, history, postmortems, replays, revocation requests, configuration |
| Gateway | AgentWorker | HTTP | Agent executions and replays, configuration |
| Gateway | Executor | HTTP | Policy, operator controls, configuration |
| Gateway | Ingestion | HTTP | Sources and their health, configuration |
| Runtime | Executor | HTTP | Plan-time policy evaluation |
| Runtime | Ingestion | HTTP | Recovery queries |
| AgentWorker | Ingestion | HTTP | Observation and knowledge queries |
| Executor | Runtime | HTTP | Start confirmation, the point of no return |
| Runtime, Executor | Gateway | HTTP | Approval verification keys, public by design |
| Each producer | Its consumers | Redis Streams | The events of [ADR-008](ADR-008-event-transport.md) and [ADR-012](ADR-012-event-semantics.md) |

## Constraints

- Approvals and operator actions keep their attestations ([ADR-006](ADR-006-remediation-control-path.md)); service authentication adds to them and never replaces them.
- The reference deployment stays cloud-neutral, so the code depends on a Sentinel-owned seam, not on one platform's identity SDK ([ADR-007](ADR-007-cross-service-code-and-provider-access.md)).
- The same authentication runs locally under Aspire as in production ([ADR-010](ADR-010-local-orchestration.md)), so tests exercise it.
- Shared code goes only into the packages ADR-007 allows; this belongs in `Sentinel.ServiceDefaults`.
- No credential is committed; local keys are generated by the AppHost, as its other secrets are.

## Considered options

1. **Trust the network.** Rely on the deployment's network policies to let only Sentinel's services talk to each other. No code, but one compromised or misconfigured workload in the network reaches everything, and nothing is tested locally.
2. **Service-mesh mutual TLS with mesh authorization policies.** Strong and invisible to the code, but it presumes Kubernetes and a particular mesh, which is the undecided environment, and it does not exist locally.
3. **Application-level mutual TLS with workload certificates,** for example SPIFFE X.509 identities. Strong and cloud-neutral, but certificate issuance and rotation in every client and a local certificate authority add the most moving parts, and Redis Streams still needs its own answer.
4. **Signed service tokens with a caller allowlist per route, and a Redis user per service.** Each call carries a short-lived token naming its caller, the receiver checks it against the callers that route allows, and Redis lets each service write only the streams it produces and read only the groups it consumes.
5. **Option 4 plus a signature on every stream message.** Protects streams even from someone holding Redis credentials, at the cost of key distribution and per-message work.

## Decision

Proposed: option 4, with message signing (option 5) deferred.

- **Tokens.** Every internal HTTP call carries `Authorization: Bearer` with a JWT whose subject is the calling service's name, whose audience is the receiving service's name, and whose lifetime is at most 10 minutes. Receivers validate issuer, audience, lifetime and signature with the standard ASP.NET Core JWT handler, under a scheme separate from the Gateway's user authentication.
- **Where tokens come from.** A Sentinel-owned `IServiceTokenSource` in `Sentinel.ServiceDefaults` obtains tokens and caches them until shortly before expiry. Its production implementation uses the deployment environment's workload identity, chosen with that environment. Locally, the AppHost generates one ES256 key pair per service at start-up, gives each service its own private key and every service the public keys, and each service issues its own tokens; nothing is written to disk or committed.
- **Who may call what.** Every internal route declares the callers it accepts, for example `[AcceptCallers("executor-service")]` on start confirmation, and refuses every other caller with 403. A route without a declaration fails an architecture test. The table above is the initial allowlist; the approval key set stays anonymous because it is public by design.
- **Streams.** Each service connects to the messaging Redis as its own ACL user, allowed to add entries only to the streams it produces and to read, claim and acknowledge only in its own consumer groups on the streams it consumes, plus its dead-letter streams. The inbox also refuses an envelope whose producer is not the stream's declared producer.
- **Operators.** Runtime's operator endpoints move behind the Gateway, which already authenticates operators and records an audit entry, and accept only the Gateway as caller.

## Consequences

### Positive

- F-013 closes: only Executor can confirm an execution start. F-007's caller half closes: every internal route names who may call it, and a test fails if one does not.
- A process that reaches the network but holds no service key can neither read incidents nor inject observations, findings or results.
- The local system runs the same checks, so the end-to-end suites prove them, and production differs only in where keys come from.

### Negative

- Every internal client gains a token handler, and every route an attribute; the AppHost gains key generation and the Redis ACL set-up.
- Stream messages are still unsigned: anyone holding a service's Redis credentials can write that service's streams. That is the same trust as holding its database credentials.
- Tenant scoping of internal reads, the other half of F-007, is not solved by this decision; internal callers are trusted to pass the right scope.

## Follow-up work

- `IServiceTokenSource`, the local self-issuing implementation and the client handler in `Sentinel.ServiceDefaults` (Phase 09).
- Caller declarations on every internal route, with an architecture test per service that finds undeclared routes (Phase 09).
- Per-service Redis ACL users in the AppHost and the producer check in the inbox (Phase 09, with a `CleanArchitecture.BuildingBlocks` release).
- Moving Runtime's operator endpoints behind the Gateway, and updating the projection rebuild and dead-letter runbooks (Phase 09).
- The production token source, once the deployment environment is chosen.
- An end-to-end test that a call without a token, or from a caller a route does not accept, is refused.

## Revisit criteria

- The chosen deployment environment provides mesh mutual TLS with workload identities that can carry the same per-route allowlist; then option 2 may replace the token source without changing the allowlists.
- Redis is shared with other systems, or the managed Redis does not support ACLs; then message signing (option 5) becomes necessary.
